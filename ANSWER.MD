# Ответы на тестовое задание

## 1. Аутентификация

В нескольких проектах у меня была авторизация через сессионные cookies, поэтому для этого проекта я бы выбрал такой же вариант.

Для обычного web-приложения мне он кажется проще JWT: сессия хранится на сервере, клиент получает `HttpOnly` cookie, а браузер сам отправляет её с запросами.

JWT я бы рассматривал, если здесь были бы несколько независимых клиентов, stateless API или другая необходимость именно в токенах.

Для этого проекта таких требований я не вижу, поэтому выбрал бы **session-based auth + HttpOnly cookie**.

---

## 2. Идентификаторы

Я бы использовал **UUID**, если ID будет уходить наружу через API.

Мне нравится, что его можно генерировать независимо от БД и по нему нельзя понять порядок создания записей.

Если ID используется только внутри БД, я бы скорее взял `BIGINT` с последовательностью. Нет смысла использовать UUID просто ради UUID.

Если выбирать UUID, я бы предпочёл **UUID v7**, а не v4, если он нормально поддерживается текущим стеком.

---

## 3. Организация кода

Из подобных подходов у меня больше всего практического опыта с разделением кода по ответственности и FSD на frontend.

В этом проекте я бы делил код по доменам и не смешивал контроллеры, бизнес-логику и работу с БД.

Если это NestJS, примерно так:

~~~text
users/
  users.controller.ts
  users.service.ts
  users.repository.ts
  dto/
~~~

Но repository и другие дополнительные слои я бы добавлял только там, где они реально нужны.

Я не люблю усложнять код заранее. Если задачу можно нормально решить одним сервисом, не вижу смысла делать ещё три слоя абстракций.

---

## 4. Реактивность

Я бы использовал React и старался держать состояние как можно ближе к месту, где оно используется.

Не стал бы сразу делать всё глобальным. Для локального состояния достаточно React, если понадобится глобальное состояние, я бы использовал Zustand.

У меня был опыт с Zustand и Effector, поэтому оба подхода мне знакомы.

Из проблем React чаще всего сталкивался с лишними `useEffect` и сложными цепочками обновлений состояния. Поэтому стараюсь не использовать `useEffect`, если значение можно просто вычислить из существующего состояния.

Если проект на Next.js, неинтерактивные части я бы по возможности оставлял Server Components, а клиентскими делал только то, что действительно требует интерактивности.

---

## 5. Рабочий процесс

Обычно сначала разбираюсь, как сейчас устроен код и что конкретно нужно изменить. После этого уже начинаю писать.

Большие задачи разбиваю на части и стараюсь сначала довести одну часть до рабочего состояния, а не несколько часов писать код, который потом впервые запускаю целиком.

Перед PR сам проверяю результат, включая основные ошибки и edge cases. После этого отправляю на review.

Если заблокирован одной задачей, переключаюсь на другую, code review или технический долг. Просто сидеть и ждать не вижу смысла.

У меня был опыт тимлида, поэтому кроме своих задач я занимался code review, архитектурой, декомпозицией и помогал другим разработчикам.

Для меня задача сделана, когда требование выполнено, всё нормально работает, очевидные ошибки обработаны и код можно отдавать на review.
